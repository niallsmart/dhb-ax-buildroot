What else is in this chip?

We are putting a modern Linux kernel on an LTS LTD2704XE-P security recorder. Networking and storage now work. This is how we worked out what else is in there — using four sources that each catch the others' mistakes, and finding along the way that we had been using half the machine.

The program

The device is an LTS LTD2704XE-P digital video recorder built on a Shenzhen TVT motherboard marked DHB_AX V1.2 — a detail worth knowing, because that string appears nowhere in the manufacturer's software. The board revision is only discoverable by looking at the hardware. Its platform is the HiSilicon Hi3531: a system-on-chip, meaning one piece of silicon containing the processor plus dozens of separate hardware blocks — network, storage, video, serial ports and so on.

It shipped running Linux 3.0.8, released in 2011. The goal is to run a current kernel on it instead. That matters because a modern kernel gets security fixes, and because the vendor's kernel is a dead end — you cannot update it, and much of it depends on binary-only drivers nobody can rebuild.

Briefer · Why porting is hard

A kernel does not automatically know what hardware exists. On a PC, firmware enumerates devices and hands the kernel a list. Embedded ARM systems have no such mechanism — the kernel must be told, in advance, that "there is a network controller at address 0x101c0000 and it interrupts on line 87."

That description lives in a device tree: a text file, compiled into a small binary, handed to the kernel at boot. Porting largely consists of writing an accurate device tree and supplying any driver code the mainline kernel lacks.

The approach: four sources that check each other

There is no single place that tells you what a board contains. There are four, each authoritative about something different and each wrong in a way the others catch. Using fewer than all four is how you end up confidently mistaken.

  1. A reference source tree — what the chip family contains

    A public mirror of HiSilicon's own kernel includes a header listing roughly eighty hardware blocks and their addresses. Broad and free to consult, but it describes a reference design, not this recorder. Treating it as the last word is the mistake an earlier draft of this page made.

  2. The vendor's own kernel and filesystem — what was really built

    We have a byte-for-byte backup of the recorder's flash, including the kernel the manufacturer compiled for this board. Decompress it and its driver names are readable. This tells you what was genuinely wired and driven — but it understates the hardware, because it omits anything the manufacturer chose not to use.

  3. The original firmware, running — what is live, and where

    Boot the factory system and read /proc/iomem and /proc/interrupts. This is the only source that gives real interrupt numbers, and it is where the biggest surprises turned up. Requires the original firmware to still be bootable.

  4. The silicon itself — what a block actually is

    Ask the hardware directly, using the trick in the next section. Slowest to gather and it goes quiet when a block is powered down, but nothing else can contradict it.

Briefer · Why four and not one

Each source has a characteristic blind spot. The reference tree overstates, listing blocks this board may not wire. The manufacturer's kernel understates, omitting working hardware they had no use for. The running system only reports what its drivers claimed. The silicon answers precisely, but only where you already thought to ask.

The concrete case: the manufacturer's kernel contains no trace of the standard ARM drivers for GPIO, SPI or the clock — they wrote their own. Consulting only that kernel, you would conclude those parts need custom drivers. Ask the silicon and it reports standard ARM designs that Linux has supported for years.

The vendor's driver files name the support chips soldered next to the SoC. These are not in the chip at all, which is exactly why the memory map alone would miss them:

  • tlv_320aic31 — a Texas Instruments audio codec
  • adv_7179 — an Analog Devices video output encoder
  • nvp1918, tw2865, tw2960 — analogue camera input decoders
  • sil9024 — a Silicon Image HDMI transmitter

The trick: asking the silicon directly

The memory map says where a block is, but not what it is. Knowing there is "an SPI controller at 0x200c0000" does not tell you whether Linux already has a driver for it.

There is a shortcut, and it rests on how this chip was built. A company like HiSilicon does not design every block from scratch. It licenses standard designs from ARM — called PrimeCell peripherals — and wires them together. We had already seen the pattern: the serial port is ARM's PL011, the timer is ARM's SP804, the storage controller is standard AHCI. All worked with drivers already in Linux.

Briefer · Registers and memory-mapped I/O

Hardware blocks are controlled through registers — small numbered storage slots that appear to software as ordinary memory addresses. Writing a value to one changes the hardware's behaviour; reading one reports its state.

So "the GPIO controller is at 0x20150000" means its first register sits at that address, with the rest following. The Linux tool devmem reads and writes these addresses directly, which is invaluable during bring-up.

Every ARM PrimeCell block is required to identify itself. At the very top of its register window sit two sets of read-only registers:

  • Peripheral ID at offset 0xFE0–0xFEC — encodes the part number
  • Cell ID at offset 0xFF0–0xFFC — always reads 0xB105F00D

That constant is a joke that has shipped in billions of devices: read as letters, B105F00D spells BLOOD FOOD. Its purpose is serious, though — if you read those four bytes and get that value, you are definitely looking at a PrimeCell block.

Worked example: validating the method

Before trusting a technique on unknowns, point it at something whose answer you already know. UART0 is the serial console this project has used since day one, and it is documented as a PL011:

Control test · UART0 at 0x20080000
# read Peripheral ID 0, Peripheral ID 1, and Cell ID 0
devmem 0x20080fe0 32   → 0x00000011
devmem 0x20080fe4 32   → 0x00000010
devmem 0x20080ff0 32   → 0x0000000D

Decoding it. The part number is split across two registers:

Decoding the part number
PID1 = 0x10  →  low 4 bits = 0x0   → part number bits [11:8]
PID0 = 0x11  →  all 8 bits = 0x11  → part number bits  [7:0]

part number = (0x0 << 8) | 0x11 = 0x011  →  PL011

CID0 = 0x0D  →  first byte of 0xB105F00D  ✓ genuine PrimeCell

The method returns the right answer on a known block, so it can be trusted on unknown ones.

Worked example: an unknown block

The GPIO controller at 0x20150000 had never been touched by this port. Same three reads:

Unknown · GPIO bank 0 at 0x20150000
devmem 0x20150fe4 32   → 0x00000010   PID1
devmem 0x20150fe0 32   → 0x00000061   PID0
devmem 0x20150ff0 32   → 0x0000000D   CID0 ✓

part number = (0x0 << 8) | 0x61 = 0x061  →  PL061

Linux has shipped a gpio-pl061 driver for years. All nineteen GPIO banks become available by adding a device tree entry — no new driver code at all.

The two that read all zeros are ambiguous rather than failed. A block whose clock is switched off reads as zeros everywhere — we saw exactly that with SATA, where every register read 0x00000000 until we enabled its clock, after which the chip identified itself immediately. So these two are either asleep or not PrimeCell designs. Distinguishing the cases needs more work.

Briefer · Why a sleeping block reads as zero

To save power, chips gate the clock signal to blocks that are not in use. Without a clock, the registers cannot respond, and the bus returns zeros rather than an error.

This is a genuine trap: it looks identical to "there is nothing here." During the SATA work it cost real time before the clock-enable register turned out to be the entire problem.

Four things fell out of that, in rough order of significance.

The processor has two cores

There are two columns in that table, not one. The factory kernel schedules work across two processors; our port declares a single one and is built with multiprocessing switched off. We have been running on half the machine since the beginning, and no amount of reading the reference source would have said so.

The recorder contains three of these chips

The PCIe bus — normally where you would find an add-in card — reports two devices, both identifying as HiSilicon part 3531. They are further copies of the same SoC, wired to the main one to handle additional camera channels. That explains a set of "host" and "slave" driver files in the factory filesystem that had not made sense before.

USB really does use the standard drivers

The suspicion is now confirmed in the strongest possible form: the firmware registers stock Linux ehci_hcd and ohci_hcd underneath a thin manufacturer-specific wrapper — precisely the arrangement our storage driver already uses. And we now have the interrupt numbers, which previously would have had to be guessed.

Both earlier guesses were right

Two interrupt numbers in this port were derived by arithmetic rather than read from any document — storage and networking. The factory firmware confirms both. That is worth knowing precisely because the same arithmetic can now be trusted elsewhere.

Briefer · Why an interrupt number matters so much

An interrupt is how a device signals that it has finished work. Give the kernel the wrong number and nothing fails immediately — setup succeeds, the device reports itself correctly, and the first real operation then hangs forever, because the completion signal arrives on a line nobody is listening to.

It is a nasty class of bug: everything looks healthy right up until it doesn't. Reading the numbers from the running factory system removes the guesswork entirely.

And it explained the two silent blocks

The DMA and I2C windows that read as all zeros are now accounted for. DMA is real and heavily used — 22,873 interrupts while we watched — so its silence was a powered-down clock. The I2C hardware, by contrast, is genuinely idle: the manufacturer drives I2C in software over general-purpose pins instead, so the dedicated block was never switched on.

Two columns repay a careful read. How we know records which source established each row: almost everything actionable came from the running firmware or from asking the silicon, and the rows resting on the reference tree alone are precisely the ones nothing has confirmed.

Vendor source is the difference between porting and inventing. Where the manufacturer's own code survives — USB, the card slot, both flash controllers, the second processor core — there is a working reference to follow, and this project has twice found that faster and more reliable than any other method. Where it does not, the work means reading compiled code or experimenting on live hardware. That single distinction moved the card slot and the main flash out of the “new driver” category entirely.

The bottom two rows deserve a blunt statement. The recorder's entire reason for existing — capturing and compressing video — is precisely the part that cannot be supported on a modern kernel, and the companion chips are unreachable for the same reason. What this port can realistically become is a capable general-purpose ARM computer with networking, storage, USB, GPIO and serial. That is a worthwhile outcome, but it is not a working DVR.

Acting on it

The survey was written as a plan. Three of its rows have since been carried out, and the results are worth recording — particularly the one that turned out to be wrong.

The second core: free, as predicted

No driver, no new code. The factory system releases the second processor by writing a start address to a specific register and nudging it awake; Linux already contains that exact procedure for a related chip, so the entire change was four lines of hardware description and one build setting. Both cores now run, and the machine stayed stable under deliberate load on both at once while moving network traffic without a single lost packet.

The pins: free, as predicted

All nineteen banks of general-purpose pins came up on the driver Linux already ships — the payoff for having asked the silicon what they were. One small local change was needed to stop the driver complaining about the absent interrupt, which had produced nineteen alarming-looking warnings at every boot.

The clock: not free, and not where I said it was

This page previously listed the clock as a free win, on the strength of the silicon reporting a standard ARM part. That was wrong in a way worth spelling out.

The part is there and Linux drives it happily — but its counter never moves, and it ignores attempts to set it. It is powered down, in the same manner as the storage controller was before we switched it on. The manufacturer's own kernel settles the question: they include a driver for that part and never load it.

What the recorder actually uses is a separate clock chip on the board, with its own battery — which matters, because the on-chip one loses its value the moment the power goes off, and a machine that cannot tell you the date at power-on is not much of a clock. Reaching that chip meant a chain of three things rather than one entry: the pin driver, a bus synthesised in software on top of it, and finally the clock chip itself.

Locating it needed two sources again. The manufacturer's compiled module revealed which two pins carry the bus but not which of the nineteen banks; the running board settled that, because exactly one bank had those two pins configured as outputs and sitting high — the signature of an idle bus held up by resistors. First attempt after that:

First boot with the clock chip described
i2c-gpio soc:i2c-gpio: using lines 612 (SDA) and 613 (SCL)
rtc-ds1307 0-0068: registered as rtc0
rtc-ds1307 0-0068: setting system clock to 2026-08-04T16:17:36 UTC

A real date, read off a battery-backed chip, on a machine that until then believed every boot began in 1970. The battery has since proved good: the time survives repeated cold starts, which is the only test that counts — an external clock chip exists precisely to keep counting while the board has no power.

Briefer · What “powered down” means here

Digital logic only draws meaningful power when it changes state, and change is driven by a clock signal. Switch that signal off and the circuit freezes, consuming almost nothing. Chips do this constantly, because any given product uses a fraction of what the silicon offers.

The trap is that a frozen block is indistinguishable from an absent one: reads return zeros, writes vanish, and no error is reported. This project has been caught by it twice. The rule that emerged: on hardware like this, reads as zero means “ask why”, never “not there”.

Recommendation

Three next steps, ordered by value earned per hour spent:

With the first two carried out, the queue is now:

  1. USB

    The highest remaining payoff. The uncertainty is largely gone: the factory system runs standard Linux drivers under a thin wrapper, we have the interrupt numbers, and the manufacturer's source for this exact chip variant survives — the same file shape that made storage work. A USB-to-serial adapter is currently plugged into the rear socket, so success has an unambiguous test: a new serial port appears.

  2. The second-level cache

    A speed improvement the port does not yet take, and another that needs description rather than code.

  3. The memory-card slot

    Genuine work — Linux has no driver for this controller — but the manufacturer's implementation is available to port from, which is a very different proposition from writing one blind.

Already done

  1. Turn on the second core

    The cheapest real gain available: no driver to write, no hardware to investigate, and it potentially doubles available processing. It is only switched off because the port began as a minimal proof that the board would boot at all, and nothing since has revisited it.

  2. The pins, and then the clock

    The pins were free as expected. The clock was not: the on-chip part is powered down and unusable, and real timekeeping turned out to sit on a separate battery-backed chip reachable only through a software bus built on those pins. Doing them in this order was accidental but necessary.

The transferable lesson

An earlier version of this page said the reference source tree answered the question "what is inside the chip." It does not. It answers "what does this family of chips generally contain" — a related but weaker claim, and the gap between the two is where a second processor core sat unnoticed.

Every source here is authoritative about something and misleading about something else. The reference tree lists blocks this board may not wire. The manufacturer's kernel omits hardware they had no use for, which would have led us to write drivers Linux already ships. The running system reports only what its drivers claimed. The silicon answers precisely, and says nothing at all when a block is powered down.

So the practical method is not to find the best source. It is to consult all of them and pay attention to where they disagree — because a disagreement is not noise, it is the interesting part. Every significant finding on this page came from exactly that.
